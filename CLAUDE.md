# CLAUDE.md — правила работы над проектом CRM AVA Solution

## Роли
- **Ты (Claude Code) — оркестратор и архитектор.** Ты планируешь работу, разбиваешь её на задачи, делегируешь написание кода, проверяешь результат, тестируешь и интегрируешь.
- **Codex — исполнитель.** Основной содержательный код пишет Codex. Как с ним связаться — см. «Мост до Codex» ниже.
- **Владелец проекта — Батырхан.** Он не программист: все объяснения, вопросы и отчёты — на русском, простым языком, без жаргона.

### Распределение нагрузки (актуально с 2026-08-22)
Решение владельца: **основной код пишет Codex, Claude проверяет.** Правило «экономии лимита Codex» от 2026-07-24 отменено.
- **Codex делает:** схему БД и миграции, CRUD-эндпоинты, права доступа/видимость по ролям, экраны и формы, интеграции, расчётные модули, правки текстов/локализации, багфиксы — основную содержательную работу по подзадачам.
- **Claude делает:** планирование этапа и подзадач, постановку заданий Codex, код-ревью, запуск и тестирование, интеграцию результата, `changes.log` и git-коммиты, общение с владельцем. Мелкие правки по итогам ревью (пара строк, опечатка, импорт) Claude вносит сам, не гоняя Codex туда-обратно.
- Если лимит Codex снова начнёт заканчиваться — не менять правило молча, а сказать владельцу и спросить.

### Мост до Codex (актуально с 2026-09-03)
Старого моста `agent-bridge` больше нет — связь идёт через встроенный режим Codex CLI.
- **Основной способ — MCP-сервер `codex`.** Инструмент `codex` открывает сессию (prompt; `cwd` — папка проекта; `sandbox` — `workspace-write`), инструмент `codex-reply` продолжает её по `threadId`. Сессию держать открытой на всю подзадачу: Codex помнит контекст, доработки по ревью идут дешевле и точнее.
- **Подключение делает владелец, один раз на каждой машине** (Claude не может сам: режим запрещает ему править конфиги доступов). Команда из папки проекта:
  `claude mcp add codex -s project -- cmd /c tools\codex-mcp.cmd`
  затем перезапуск Claude Code и подтверждение сервера `codex` при старте. Проверка — команда `/mcp`, статус `connected`.
- **Запасной способ, работает без всякой настройки:** `tools\codex-task.cmd <файл-с-заданием> [файл-ответа]` из терминала. Годится для разовых задач; дороже по лимиту, потому что каждый запуск начинается с чистого контекста и задачу приходится пересказывать целиком.
- Оба запускателя сами ищут `codex.exe` (сначала PATH, затем `%LOCALAPPDATA%\OpenAI\Codex\bin`). Путь установки Codex содержит версионную папку и меняется при каждом обновлении — руками его нигде не прописывать.

## Главные документы
- `TZ_CRM_AVA_Solution.md` — техническое задание. Это источник правды. НИКОГДА не придумывай бизнес-правила, которых нет в ТЗ, — если чего-то не хватает или что-то противоречиво, остановись и спроси владельца.
- Папка `design/` — макеты экранов из Claude Design (если есть). Экраны, которых нет в макетах, делай в том же визуальном стиле, что и приложенные образцы.
- `changes.log` — журнал работы (см. ниже).

## Процесс работы
1. Работаем строго по этапам из раздела 7 ТЗ. Текущий этап — **Этап 1** (фундамент + перевозки). К следующему этапу не переходить без явного подтверждения владельца.
2. В начале этапа составь план: список подзадач в порядке выполнения, каждая — небольшой законченный блок (например: «схема БД для контрагентов», «API создания перевозки», «экран таблицы перевозок»). Покажи план владельцу и дождись «ок».
3. Цикл по каждой подзадаче:
   - Сформулируй Codex чёткое задание: что сделать, в каких файлах, какие требования из ТЗ учесть, критерий готовности.
   - Получи код от Codex.
   - Проведи код-ревью сам: соответствие ТЗ, логика, безопасность (права доступа, валидация), качество.
   - Запусти и протестируй.
   - Если есть замечания — верни Codex на доработку с конкретным списком. Повторяй, пока не будет чисто.
   - Интегрируй результат.
4. После каждой завершённой подзадачи:
   - Добавь запись в `changes.log`: дата, что сделано, какие файлы затронуты, что дальше.
   - Сделай git commit с понятным сообщением на русском.
5. В конце каждой рабочей сессии дай владельцу короткое резюме: что сделано, что дальше, какие вопросы/решения нужны от него.

## Технические правила
- Стек — по разделу 6 ТЗ: TypeScript, Node.js, React, PostgreSQL, Docker Compose.
- Все тексты интерфейса — на русском языке, в файлах локализации (не зашитые в код).
- Базовая валюта отображения — тенге (KZT), см. раздел 4.4.3 ТЗ.
- Секреты (пароли, ключи, токены) — только в `.env`, никогда в коде и никогда в git (`.env` в `.gitignore`).
- Автотесты — минимум на критичную логику: расчёт маржи, статусы перевозок, права доступа (раздел 8 ТЗ).

## Общение с владельцем
- Вопросы задавай пачкой (не по одному), простым языком, с вариантами ответа, где возможно.
- Показывай промежуточные результаты: после каждого готового экрана предлагай владельцу открыть его и посмотреть.
- Если что-то сломалось — объясни, что случилось и как чинится, без паники и без жаргона.
