# Техническое задание: CRM-система для экспедиторской компании

**Заказчик:** ТОО AVA Solution (также ТОО ALT Corp, ИП Transit Trail)
**Версия документа:** 1.0
**Дата:** июль 2026
**Назначение документа:** это ТЗ предназначено для разработки системы с помощью AI-агентов (Claude Code + Codex) и для контроля результата заказчиком.

---

## 1. Общие сведения

### 1.1. О компании
Компания — экспедитор (freight forwarder), организует грузоперевозки по коридору Китай → Казахстан → СНГ, а также внутри Казахстана и из Европы. Компания не владеет транспортом: она принимает заявку от клиента и привлекает субподрядчиков (перевозчиков, таможенных брокеров, склады) для выполнения перевозки. Деятельность ведётся через несколько юридических лиц: ТОО AVA Solution (основной бренд), ТОО ALT Corp, ИП Transit Trail.

### 1.2. Цель проекта
Заменить Bitrix24 собственной системой, которая объединяет: учёт клиентов и контрагентов, ведение сделок и перевозок, финансы (счета, платежи, маржа по сделкам), документооборот (генерация договоров, счетов, актов) и коммуникации (WhatsApp через Wazzup, телефония).

### 1.3. Ключевые проблемы, которые система должна решить
1. Статусы грузов сейчас ведутся вручную/разрозненно — команда и руководство не видят единой картины по всем перевозкам.
2. Финансовая картина по сделке (сколько заплатил клиент, сколько ушло субподрядчикам, какая маржа) собирается вручную.
3. Документы (договоры, счета, акты) создаются копированием старых файлов — долго и с ошибками.
4. Переписка с клиентами в WhatsApp и звонки не привязаны к сделкам.
5. Работа через три юрлица требует постоянно помнить, от какого лица выставлять документы.

### 1.4. Пользователи
- Количество: 6–15 сотрудников.
- Доступ: веб-приложение через браузер с рабочих компьютеров (Windows). Мобильная версия — на следующем этапе, поэтому интерфейс сразу проектируется адаптивным (mobile-friendly вёрстка), но отдельное мобильное приложение в текущий объём не входит.
- Язык интерфейса: русский. Архитектура должна позволять добавить другие языки позже (все тексты интерфейса — в отдельных файлах локализации, не «зашиты» в код).

## 2. Термины

| Термин | Значение |
|---|---|
| Клиент | Компания или ИП, заказывающая перевозку |
| Контрагент | Общее название: клиент, перевозчик, брокер, склад, поставщик услуг |
| Субподрядчик | Перевозчик/брокер/склад, привлекаемый для исполнения перевозки |
| Сделка | Один коммерческий заказ клиента (может включать одну или несколько перевозок). НЕ путать с договором: договор — юридическая рамка (подписывается один раз, живёт в карточке контрагента), сделка — конкретный заказ по этому договору; по одному договору может быть много сделок. Сделка всегда ведётся от одного юрлица группы |
| Перевозка (груз) | Конкретная отправка груза из точки А в точку Б, возможно через несколько участков |
| Участок маршрута (leg) | Часть перевозки, выполняемая одним субподрядчиком (например: Гуанчжоу → Хоргос, Хоргос → Алматы) |
| Юрлицо | Одна из компаний группы, от имени которой ведётся сделка и выставляются документы |

## 3. Роли и права доступа

Система должна иметь ролевую модель. **Роли комбинируемые: одному пользователю можно назначить несколько ролей одновременно** (частый случай в компании — менеджер и логист в одном лице: сотрудник сам находит клиента, перевозчика и считает ставку). Права нескольких ролей суммируются.

**Отделы.** У каждого пользователя и каждой сделки есть атрибут «отдел» (справочник, расширяемый; на старте: отдел Китая, направление РК/РФ). Отдел сделки по умолчанию наследуется от ответственного.

Минимальный набор ролей:

| Роль | Что видит и может |
|---|---|
| Администратор | Всё: настройки системы, пользователи, справочники, все данные |
| Руководитель | Все сделки, финансы, отчёты; без настроек системы |
| Руководитель отдела | Все сделки, перевозки и маржа СВОЕГО отдела; сводная мотивация по сотрудникам своего отдела; назначение ответственных внутри отдела; всё, что умеет менеджер+логист. НЕ видит другие отделы, общую финансовую отчётность компании и внутригрупповые операции |
| Менеджер | Свои сделки и клиенты + просмотр общих справочников; создание сделок, перевозок, счетов; **видит грязную маржу по своим сделкам** (мотивация и самоконтроль); НЕ видит чужие сделки и их маржу, общую финансовую отчётность и внутригрупповые операции |
| Логист | **Только свои перевозки** (где он ответственный): статусы, участки, субподрядчики; без финансов клиентов (счета и ставки клиентов не видит); **видит свой личный отчёт мотивации** (итоговая маржа и бонус по своим перевозкам). Перевозки коллег не видит; при отпуске/болезни руководитель отдела переназначает ответственного |
| Финансист | Все финансы: счета, платежи, кассовый календарь, курсы валют; без права менять статусы перевозок |

Требования:
- Права назначаются администратором через интерфейс, без программиста.
- Каждое действие пользователя с данными (создание, изменение, удаление сделки/счёта/платежа) записывается в журнал: кто, когда, что изменил (старое значение → новое значение).
- Удаление важных сущностей (сделка, счёт, платёж) — только «мягкое» (запись помечается удалённой, но остаётся в базе и может быть восстановлена администратором).
- **Деактивация сотрудника:** администратор отключает доступ пользователя (учётная запись блокируется, но не удаляется — вся история его действий сохраняется). При деактивации система обязательно предлагает массово переназначить его активные сделки и перевозки другому ответственному (мастер переназначения: выбрал нового ответственного → все открытые сущности перешли к нему). Переписка WhatsApp с корпоративного номера остаётся в системе и не зависит от ухода сотрудника.

## 4. Функциональные модули

### 4.1. Модуль «Контрагенты»

Единый справочник всех компаний, с которыми работает группа.

Карточка контрагента:
- Тип: клиент / перевозчик / таможенный брокер / склад / поставщик / прочее (может быть несколько типов одновременно).
- Реквизиты: наименование, БИН/ИИН (для Казахстана), страна, юридический адрес, банковские реквизиты (может быть несколько счетов в разных валютах).
- Контактные лица: ФИО, должность, телефон, email, WhatsApp; контактов может быть несколько.
- Договоры с контрагентом — реестр в карточке: номер, дата, от какого юрлица группы, срок действия, файл скана, статус (действует / истёк / расторгнут). Номер вводится вручную (существующие бумажные договоры сохраняют свои номера) либо присваивается автоматически при генерации договора из системы (шаблон нумерации настраивается, номер можно поправить). У одной пары «юрлицо группы ↔ контрагент» может быть несколько договоров. Уведомление об истечении срока договора за N дней (настраивается, по умолчанию 30).
- Условия оплаты по умолчанию: предоплата / постоплата N дней.
- Заметки и файлы (вложения).
- История: все сделки, перевозки, звонки и сообщения WhatsApp, связанные с этим контрагентом (см. интеграции).

Требования:
- Поиск по названию, БИН, телефону, контактному лицу.
- Проверка на дубли при создании (по БИН и по названию).
- **Парсер реквизитов из текста.** При создании/редактировании контрагента — поле «Вставить реквизиты текстом»: пользователь вставляет реквизиты одним блоком (как их прислали в WhatsApp/email), система распознаёт и раскладывает по полям (наименование, БИН/ИИН, банк, номер счёта, адрес, телефон), пользователь проверяет и подтверждает. Логика переиспользуется из существующего приложения docs.ava-solution.kz, где эта функция уже реализована. Работает и для перевозчиков, и для клиентов. **Форма создания контрагента после распознавания показывает все распознанные поля для проверки** (БИН/ИИН, название, банк, номер счёта — счетов может быть несколько, адрес, телефон) — распознанные данные не должны отбрасываться. Обязательный минимум для сохранения: тип, название, БИН/ИИН; остальные реквизиты дозаполняются по мере наличия. Кнопки «Сохранить» и «Сохранить и открыть карточку» (для дозаполнения контактов, договоров, условий оплаты).
- **Качество перевозчиков.** Специфика компании: по китайскому направлению перевозчики в основном постоянные, по РК и РК→СНГ ~80% — новые водители. Поэтому: (а) при подборе субподрядчика в перевозку — автодополнение с сортировкой по частоте работы на данном направлении (постоянные перевозчики Китая — в два клика); (б) после завершения перевозки — быстрая оценка перевозчика (норм/были проблемы + комментарий), история оценок в карточке; (в) флаг «первая перевозка с этим контрагентом» подсвечивается в карточке перевозки; (г) чёрный список: метка «не работаем» с причиной — при попытке выбрать такого перевозчика система предупреждает; (д) со временем накапливается собственная база проверенных водителей по РК/СНГ.
- Метка «проблемный контрагент» с комментарием (например, после споров типа кейса с ТОО World Agro Trade) — видна всем при открытии карточки.

### 4.2. Модуль «Сделки»

Сделка — центральная сущность, связывающая клиента, перевозки, финансы и документы.

Карточка сделки:
- Номер (автоматический, сквозной, с префиксом юрлица, например AVA-2026-0145).
- Клиент (из справочника контрагентов).
- Юрлицо группы, от которого ведётся сделка (AVA Solution / ALT Corp / Transit Trail) — обязательное поле.
- **Договор-основание.** При выборе клиента и юрлица система автоматически подставляет действующий договор между ними из реестра договоров контрагента (если их несколько — выбор из списка; если договора нет — предложение «Сгенерировать договор» через модуль документов, созданный договор автоматически попадает в реестр контрагента и привязывается к сделке). Номер и дата договора из сделки подставляются во все генерируемые документы («к договору №___ от ___»). Аналогично на стороне субподрядчика: транспортная заявка перевозчику ссылается на договор юрлица группы с этим перевозчиком из его карточки.
- Ответственный менеджер.
- Стадия сделки (воронка): Новая заявка → Расчёт ставки → Ставка отправлена → Согласована → В работе (перевозка) → Выполнена → Закрыта (оплачена полностью). Плюс стадия «Отказ» с обязательным указанием причины.
- Перевозки внутри сделки (одна или несколько).
- Финансовый блок: см. модуль «Финансы» — доходы, расходы, маржа считаются автоматически.
- Документы по сделке: договор-заявка, счета, акты, CMR/накладные — генерируются или прикрепляются.
- **Принцип интерфейса: в типовом сценарии сделка не мешает.** Для частого случая «один заказ = одна перевозка» пользователь работает только с перевозкой: создание через форму «Создать сделку + перевозку», основной рабочий экран — таблица перевозок, а в карточке такой перевозки финансовый блок её сделки (счёт, оплаты, маржа) отображается прямо в карточке — открывать сделку отдельно не требуется. Сделка как отдельный экран нужна, когда в заказе несколько перевозок, при работе с воронкой (расчёты ставок, отказы, лиды с сайта) и при выставлении общего счёта.
- Лента активности: изменения, комментарии сотрудников, привязанные звонки и сообщения.

Требования:
- Канбан-доска сделок по стадиям + табличный вид со сортировкой и фильтрами (по менеджеру, юрлицу, клиенту, датам).
- Обязательная причина при переводе в «Отказ» (выбор из списка: дорого, сроки, ушёл к конкуренту, не вышел на связь, другое + комментарий).
- Напоминания: если сделка в стадии «Ставка отправлена» без движения более N дней (настраивается) — уведомление менеджеру.

### 4.3. Модуль «Перевозки» (трекер грузов)

Карточка перевозки:
- Номер (автоматический, связан с номером сделки: AVA-2026-0145/1).
- Описание груза: наименование, количество мест, вес (кг), объём (м³), стоимость груза и валюта (для страховки/ответственности), опасный груз (да/нет), температурный режим (если нужен).
- Маршрут: пункт отправления, пункт назначения (свободный ввод: город + страна). Статусы и логика не должны быть привязаны к конкретной географии — система должна одинаково работать для Китай→КЗ, внутриказахстанских, КЗ→СНГ и европейских маршрутов.
- Вид транспорта: авто / ж/д / море / авиа / мультимодальная.
- Участки маршрута (legs), каждый содержит: откуда → куда, субподрядчик (из справочника), вид транспорта, ставка субподрядчика и валюта **+ признак «с НДС / без НДС»** (печатается в заявке перевозчику и учитывается в финансах), плановые даты, фактические даты, номер машины/контейнера/вагона, статус участка.
- **Типовой случай — один перевозчик на всю перевозку (большинство перевозок компании).** При создании перевозки участок создаётся автоматически один и в интерфейсе не показывается как отдельная сущность: пользователь заполняет простую форму (перевозчик, ставка, маршрут, даты) без упоминания «участков». Кнопка «Разбить на участки» переводит перевозку в многоучастковый режим (для мультимодальных и составных маршрутов). Обратное объединение возможно, пока заполнен только один участок.
- **Привязка к сделке обязательна.** Перевозка не может существовать без сделки (на сделке держатся клиент, юрлицо, счета и маржа). Чтобы это не создавало бюрократии: в форме создания перевозки — выбор существующей сделки ИЛИ кнопка «Создать сделку + перевозку» (одна форма, сделка создаётся автоматически с согласованным номером). У одной сделки может быть несколько перевозок.
- **Ставка клиента.** Отдельное поле карточки перевозки: согласованная с клиентом цена перевозки (+ валюта). Заполняется менеджером на этапе согласования; после выставления счёта изменение ставки — с предупреждением и записью в журнал. На уровне сделки показывается сумма ставок всех её перевозок. Ставка клиента автоматически подставляется в транспортную заявку клиенту и в создаваемый счёт («Создать счёт на ставку» одной кнопкой). Видимость по ролям: менеджер (свои), руководитель отдела (свой отдел), руководитель/финансист/админ; логист ставку клиента не видит.
- **Маржа перевозки в двух видах:** плановая = ставка клиента − сумма ставок субподрядчиков (отображается сразу после заполнения ставок, до счетов и оплат) и фактическая = по реальным счетам и оплатам с фактическими курсами (см. 4.4.3). В карточке перевозки и сделки показываются обе с расхождением («план / факт»); вычисляемые колонки и отчёт мотивации используют фактическую маржу, а до появления оплат — плановую с пометкой «прогноз».
- **Мастер создания перевозки (пошаговая форма).** Требования к мастеру: (а) ставка клиента вводится на том же шаге, где маршрут и ставка перевозчика; (б) под ставками — живая строка «Плановая маржа: сумма и %», пересчитывается при вводе; (в) поля «Ставка клиента» и маржа отображаются в мастере только ролям, которым разрешена ставка клиента (чистый логист их не видит, заполняются менеджером позже в карточке); (г) финальный шаг «Проверка» включает финансовую сводку: ставка клиента, ставка перевозчика, плановая маржа; (д) на шаге проверки — галочки «Сгенерировать заявку перевозчику» и «Сгенерировать заявку клиенту»; (е) черновик мастера сохраняется автоматически; (ж) логика шага «Маршрут и перевозчик» — по потоку сделки: маршрут (откуда/куда) → блок «Клиент» (ставка клиента) → блок «Перевозчик» (субподрядчик, ставка, плановый забор, машина, водитель и его документы — внутри блока перевозчика) → итоговая выделенная строка «Плановая маржа» в тенге внизу; (з) плановая маржа в мастере и карточке отображается в тенге (базовая валюта, см. 4.4.3); (и) **состав мастера — минимально необходимое на момент фиксации ставки**: сделка/клиент/юрлицо/ответственный, груз, маршрут (города), ставки, водитель (необязательно). Данные для транспортных заявок (адреса и время погрузки/выгрузки, контакты на точках, грузоотправитель/грузополучатель, тип кузова, сопроводительные документы, особые условия) в мастер НЕ входят — они заполняются позже в карточке перевозки.
- **Раздел «Данные для заявки» в карточке перевозки.** Все поля, нужные для транспортных заявок (адреса, контакты, грузоотправитель/грузополучатель, тип кузова, сопроводительные документы, особые условия, водитель), собраны в отдельном разделе карточки с **индикатором заполненности** («для заявки перевозчику заполнено 8 из 12 полей») — сразу видно, каких данных ещё ждём от клиента/перевозчика. Здесь же — кнопки «Сгенерировать заявку перевозчику» и «Сгенерировать заявку клиенту».
- **Денежные поля.** Везде в системе денежное поле — это число + отдельный селектор валюты (два разных элемента), а не текст «380 000 KZT» одной строкой: суммы должны быть пригодны для расчётов и конвертаций. Относится к ставкам, стоимости груза, счетам, платежам.
- Общий статус перевозки — 6 статусов: **Заявка принята → Груз забран → В пути → Таможня → Доставлен → Закрыта**. Статус «Таможня» может наступать между любыми участками. Разрешён откат статуса назад (с записью в журнал).
- Плановая и фактическая дата доставки.
- Документы перевозки: инвойс, упаковочный лист, CMR, ж/д накладная, таможенная декларация — прикрепляются файлами к карточке.
- **Данные и документы водителя.** В перевозке (в простом режиме — прямо в основной форме, в многоучастковом — в каждом участке): ФИО водителя, телефон, ИИН, № удостоверения (в/у), дата выдачи и кем выдано (текстовые поля — печатаются в транспортной заявке), номер машины/прицепа + загрузка документов водителя (удостоверение, техпаспорт, доверенность и т.п.) **доступна уже при создании перевозки** — типовой сценарий: при фиксации ставки перевозчик сразу присылает данные водителя, и они вносятся одним заходом. Данные водителя автоматически подставляются в транспортную заявку перевозчику. Загруженные документы видны также в карточке контрагента-перевозчика (история по его водителям).
- **Грузоотправитель и грузополучатель.** Отдельные поля перевозки: грузоотправитель (организация на точке погрузки) и грузополучатель (организация на точке выгрузки) — свободный ввод или выбор из справочника контрагентов. Могут не совпадать с клиентом сделки (клиент заказывает и платит, отправляет и получает груз часто третья сторона). Печатаются в транспортных заявках.
- **Сопроводительные документы.** Поле перевозки: перечень сопроводительных документов (мультивыбор из справочника: CMR, СНТ, ТТН, доверенность и т.п. + свободный ввод) — печатается в заявке перевозчику.
- Количество мест указывается с единицей упаковки (мест: число + единица — паллеты / коробки / ролики / и т.п., справочник расширяемый).
- **Адреса и контакты погрузки/выгрузки.** Помимо городов маршрута: точный адрес погрузки, дата и время погрузки, контактное лицо на погрузке (имя, телефон); точный адрес выгрузки, контактное лицо на выгрузке; требования к транспорту (тип кузова: тент / рефрижератор / контейнер / открытая платформа и т.п., справочник); «Особые условия / примечания» (свободный текст: простой, штрафы, специфика). Все эти поля необязательны при создании (точные адреса часто приходят позже фиксации ставки) и заполняются в карточке перевозки (раздел «Данные для заявки») или на экране предпросмотра при генерации; в мастер создания перевозки эти поля не входят.

Требования:
- Главный экран логиста: таблица всех активных перевозок со статусами, цветовая индикация просрочки (фактическая дата позже плановой — строка подсвечивается).
- **Настраиваемые колонки таблиц (общее требование для всех основных табличных экранов системы: перевозки, сделки, счета, контрагенты).** Над каждой большой таблицей — кнопка «Колонки»: пользователь включает/выключает отображение отдельных колонок (например, скрыть «Вид транспорта») и меняет их порядок перетаскиванием. Настройки индивидуальны для каждого пользователя и хранятся на сервере (сохраняются при входе с любого устройства). Ограничение: в списке доступных колонок присутствуют только те, что разрешены роли пользователя — настройка отображения не может открыть данные, скрытые правами доступа (менеджер не может «включить» колонку с маржой или ставкой субподрядчика, если роль её не видит). Для каждой роли администратор задаёт стартовый набор колонок по умолчанию; у пользователя есть кнопка «Сбросить к стандартному виду».
- **Максимальная вариативность колонок.** Принцип: любое поле карточки соответствующей сущности автоматически доступно как колонка таблицы (при добавлении нового поля в систему оно само появляется в списке доступных колонок). Для таблицы перевозок это означает в том числе: дата погрузки (план/факт), дата выгрузки (план/факт), клиент, субподрядчики, номер машины/контейнера, вес, объём, вид транспорта, маршрут, ответственный и т.д. Дополнительно доступны **вычисляемые колонки**: грязная маржа (сумма и %), оплачено клиентом (%), оплачено субподрядчикам (%), дней в пути, просрочка (дней), количество участков. Финансовые и вычисляемые колонки подчиняются правам роли: например, «Грязная маржа» присутствует в списке доступных колонок только у ролей, которым разрешено видеть маржу.
- История смены статусов с датой, временем и автором.
- **Дата события ≠ дата нажатия кнопки.** При переводе в статус «Доставлен» система запрашивает фактическую дату выгрузки (по умолчанию — сегодня, можно выбрать прошедшую дату: статус часто проставляют на следующий день после события). В журнале сохраняются обе даты: фактическая дата выгрузки (бизнес-факт — используется для зарплаты и отчётов) и дата/время проставления статуса (для контроля дисциплины ввода). Аналогично для даты забора груза при статусе «Груз забран». Будущие даты запрещены.
- При смене статуса — возможность (галочка) отправить клиенту уведомление в WhatsApp через Wazzup с шаблонным текстом (см. интеграции).

### 4.4. Модуль «Финансы»

Ключевой принцип: каждая денежная операция привязана к сделке и к юрлицу. Это позволяет автоматически видеть маржу по каждой сделке и картину по каждому юрлицу.

#### 4.4.1. Доходы (счета клиентам)
- Создание счёта из сделки: юрлицо-плательщик берётся из карточки клиента, юрлицо-получатель — из сделки.
- Поля счёта: номер (автонумерация в рамках юрлица и года), дата, клиент, сделка, позиции (услуга, количество, цена), валюта, сумма, срок оплаты, статус (Выставлен → Частично оплачен → Оплачен → Просрочен).
- Фиксация оплат: дата, сумма, валюта; частичная оплата допускается (несколько платежей на один счёт).
- НДС: по каждой позиции признак «с НДС / без НДС» и ставка. Учесть, что при смешанных экспедиторских операциях в Казахстане НДС применяется по-разному — ставка НДС должна задаваться на уровне позиции счёта, а не жёстко на весь счёт.

#### 4.4.2. Расходы (платежи субподрядчикам и поставщикам)
- Заявка на оплату: создаётся из участка перевозки (сумма и получатель уже известны из участка) или вручную; поля: получатель, сделка/перевозка, сумма, валюта, срок оплаты, назначение, счёт-основание (файл).
- Статусы: Заявлен → Согласован → Оплачен. Согласование — руководителем или финансистом (настраивается).
- Прочие расходы, не привязанные к сделке (аренда, зарплата и т.п.), — отдельная категория «Операционные расходы» с типами.

#### 4.4.3. Валюты
- Мультивалютность обязательна: KZT, USD, CNY, RUB, EUR (список расширяемый).
- **Базовая валюта системы — KZT (тенге).** Все вычисляемые и сводные показатели (маржа, итоги по сделкам, отчёты, дашборд, мотивация) по умолчанию отображаются в тенге; суммы в других валютах приводятся к тенге по применимому курсу (фактическому курсу оплаты или курсу НБ РК — см. ниже). Исходная валютная сумма при этом всегда доступна рядом или по наведению (например: «3 000 USD ≈ 1 620 000 ₸»). Базовая валюта — параметр системных настроек, по умолчанию KZT.
- Курсы валют: подтягиваются автоматически с курса Нацбанка РК раз в день + возможность вручную задать внутренний курс на дату.
- **Фактический курс по каждой оплате.** При фиксации любой оплаты (входящей от клиента или исходящей субподрядчику) пользователь может вручную указать фактический курс этой конкретной операции (курс банка/обменника, по которому реально прошли деньги). Если фактический курс не указан — используется курс НБ РК на дату оплаты.
- Логика расчёта маржи по сделке: по операциям, где оплата уже прошла, — по фактическим курсам оплат; по ещё не оплаченным суммам — по текущему курсу НБ РК как прогноз. В карточке сделки маржа показывается с пометкой «прогноз», пока есть неоплаченные суммы, и становится финальной после всех оплат.
- Типовой сценарий для тестирования: клиент платит в USD после выгрузки, перевозчик из Китая получает оплату в CNY сразу — курсовая разница между датами оплат должна корректно отражаться в марже сделки (отдельная строка «курсовая разница» в финансовом блоке сделки).

#### 4.4.4. Маржа и кассовый календарь
- В карточке сделки автоматически: сумма доходов, сумма расходов, маржа (в деньгах и %), сколько клиент уже оплатил, сколько мы уже заплатили субподрядчикам.
- Кассовый календарь: экран «ожидаемые поступления и обязательные платежи по дням/неделям» на основе сроков оплат счетов и заявок — чтобы видеть кассовые разрывы заранее.
- Отчёт «Дебиторка»: кто из клиентов сколько должен и как давно просрочил.
- Отчёт «Кредиторка»: кому мы должны и когда.

#### 4.4.5. Налоговые режимы юрлиц
- У каждого юрлица группы разный налоговый режим и способ расчёта налогов. Логика расчёта **не зашивается в код** под конкретное юрлицо — она задаётся структурированными настройками в карточке юрлица (раздел «Настройки → Юрлица»), которые администратор/финансист меняет без программиста.
- Параметры карточки юрлица: налоговый режим (справочник: общеустановленный / упрощённый / иной СНР), плательщик НДС (да/нет) и ставка НДС, ставка налога с дохода для управленческого расчёта, прочие параметры при необходимости.
- Все ставки задаются **с датой начала действия** (история ставок): при изменении ставки прошлые операции продолжают считаться по ставкам, действовавшим на их дату; пересчёт истории задним числом запрещён.
- Система использует эти параметры для: (а) правильного НДС в счетах и документах юрлица; (б) управленческого расчёта «чистой» маржи по сделке с учётом налогов юрлица; (в) отчётов в разрезе юрлиц.
- Изменение налоговых настроек записывается в журнал (кто, когда, что изменил).
- Граница ответственности: CRM считает налоги для управленческого учёта и корректных документов; официальная налоговая отчётность и декларации остаются в бухгалтерской программе и не входят в объём системы.
- **Юрлица группы — расширяемый справочник, а не фиксированный список.** Администратор может добавить новое юрлицо (ИП или ТОО) со всеми реквизитами, префиксом нумерации и налоговыми настройками без участия программиста; новое юрлицо сразу доступно при создании сделок и документов.
- Справочные данные для настройки и тестирования (текущее состояние, задаётся настройками, НЕ зашивается в код): ИП Transit Trail — ОУР, ИПН 10%, без НДС (планируется постановка на учёт по НДС 16% — тестовый сценарий для истории ставок); ТОО AVA Solution — ОУР, КПН 20%, плательщик НДС; ТОО ALT Corp — ОУР, без НДС.

#### 4.4.6. Внутригрупповые операции (перевыставление расходов)
- Ситуация: расход по сделке оплачен одним юрлицом группы, а сделка ведётся от другого. Такие случаи бывают регулярно и должны корректно отражаться.
- Каждое юрлицо группы автоматически существует в системе и как контрагент — чтобы юрлица могли выставлять счета друг другу. Операции, где обе стороны — юрлица группы, автоматически помечаются флагом «внутригрупповая».
- В карточке расхода — действие «Перевыставить на другое юрлицо»: система создаёт внутренний счёт от оплатившего юрлица к юрлицу сделки, привязанный к той же сделке; сумма и основание копируются из исходного расхода. По внутреннему счёту можно сгенерировать документ (счёт/акт) по обычным шаблонам.
- Отчётность на двух уровнях: отчёт по отдельному юрлицу включает внутригрупповые операции; сводный отчёт по группе автоматически исключает их (элиминация), чтобы обороты и маржа не задваивались.
- Внутригрупповые операции визуально помечены в списках (иконка/цвет), фильтр «показать только внутригрупповые».
- **Доступ:** раздел внутригрупповых операций (создание перевыставлений, внутренние счета, их списки и отчёты) виден и доступен только ролям Финансист, Руководитель и Администратор. Менеджеры и логисты этих операций не видят.

#### 4.4.7. Зарплата и мотивация сотрудников
- В карточке перевозки обязательное поле **«Дата выгрузки (факт)»** — заполняется при переводе в статус «Доставлен».
- Ключевое правило учёта: **для расчёта зарплаты/бонусов перевозка относится к тому месяцу, в котором произошла фактическая выгрузка** (не к месяцу создания сделки и не к месяцу оплаты).
- Отчёт «Мотивация за месяц»: выбирается месяц → система показывает все перевозки, выгруженные в этом месяце, сгруппированные по ответственному менеджеру, с выручкой и маржой по каждой; итог по менеджеру.
- **«Мой отчёт мотивации» (личный кабинет сотрудника):** каждый менеджер и логист видит собственный отчёт за месяц — свои перевозки, выгруженные в этом месяце, маржу по каждой и расчётный бонус. Видит только себя; сводный отчёт по всем сотрудникам доступен только Руководителю, Финансисту и Администратору. Расхождения «сотрудник видит одно, бухгалтерия платит другое» исключаются: источник правды для выплаты — именно этот отчёт.
- Формула бонуса: **по умолчанию 10% от грязной маржи** перевозок сотрудника (менеджера/логиста), выгруженных в расчётном месяце. Ставка редактируется в настройках; возможна индивидуальная ставка по конкретному сотруднику (переопределяет общую).
- **Бонус начисляется независимо от факта оплаты клиентом** (неоплата — не вина менеджера). При этом в отчёте «Мотивация за месяц» по каждой перевозке справочно показывается статус оплаты клиентом (оплачено полностью / частично / не оплачено) — для прозрачности, без влияния на начисление.
- Поскольку маржа неоплаченных сделок считается по прогнозному курсу (см. 4.4.3), бонус рассчитывается от маржи на момент расчёта; правила пересчёта при существенном изменении курса после оплаты — на усмотрение руководителя, система пересчёт автоматически не делает, но показывает разницу.
- Если дата выгрузки корректируется задним числом после закрытия месяца — система предупреждает и пишет изменение в журнал (это влияет на уже рассчитанную зарплату).
- Во всех финансовых отчётах — переключатель базы периода: «по дате выгрузки / по дате оплаты / по дате создания сделки».

### 4.5. Модуль «Документы»

У компании уже есть работающее приложение генерации документов — **docs.ava-solution.kz** (Node.js, Word-шаблоны с автозаполнением реквизитов по выбору юрлица). Оно является основой этого модуля.

#### 4.5.1. Интеграция с существующим приложением
- Перед разработкой модуля разработчик (AI-агент) получает доступ к исходному коду docs.ava-solution.kz и **переиспользует его шаблоны и логику автозаполнения**, перенося их внутрь CRM (предпочтительный вариант), либо — если перенос окажется сложным — CRM обращается к существующему приложению по API, передавая данные сделки.
- Критерий выбора варианта: пользователь не должен вводить данные дважды. Всё, что уже есть в карточке сделки/перевозки (клиент, реквизиты, маршрут, суммы), подставляется в документ автоматически.
- Существующие наработки по реквизитам трёх юрлиц (AVA Solution / ALT Corp / Transit Trail) переносятся как есть.

#### 4.5.2. Типы документов и откуда они создаются
| Документ | Создаётся из | Кто стороны документа |
|---|---|---|
| Договор с клиентом | Карточка сделки | Юрлицо группы ↔ Клиент |
| Транспортная заявка для клиента | Карточка сделки / перевозки | Юрлицо группы ↔ Клиент (маршрут, груз, ставка клиента, условия) |
| Транспортная заявка для перевозчика | Участок маршрута (leg) | Юрлицо группы ↔ Субподрядчик (участок, груз, ставка субподрядчика, номер машины/контейнера) |
| Счёт на оплату | Счёт | Юрлицо группы ↔ Клиент |
| Акт выполненных работ | Сделка / счёт | Юрлицо группы ↔ Клиент |
| Доверенность | Карточка сотрудника/перевозки | По шаблону |

Важно: заявка для клиента и заявка для перевозчика — это разные документы с разными суммами (ставка клиента ≠ ставка субподрядчика), система никогда не должна показать субподрядчику ставку клиента и наоборот. При генерации заявки для перевозчика данные берутся только из участка маршрута.

#### 4.5.3. Общие требования
- Шаблоны хранятся как файлы Word (.docx) с плейсхолдерами (например {{client_name}}, {{deal_number}}, {{amount}}); администратор может загружать и править шаблоны без программиста.
- Генерация нажатием кнопки из соответствующей карточки; результат — .docx и PDF; сгенерированный файл автоматически прикрепляется к карточке.
- **Предпросмотр и дозаполнение при генерации.** Нажатие «Сгенерировать» открывает предзаполненную форму со всеми полями документа: известные системе данные подставлены, недостающие (адреса, контакты, особые условия) подсвечены пустыми и заполняются на месте. Введённые значения сохраняются обратно в карточку перевозки/сделки — повторная генерация не требует повторного ввода. Условия оплаты подставляются из карточки контрагента (условия по умолчанию) с возможностью изменить для конкретной заявки. Документ не формируется, пока не заполнены поля, обязательные для данного шаблона (настраивается в шаблоне).
- **Справочник типовых текстов оплаты.** Администратор ведёт библиотеку готовых формулировок «Способ оплаты» и «Условия оплаты» (например: «Оплата 100% безналичный расчёт после выгрузки с предоставлением фото/видео, сканов подписанных отгрузочных документов, ТТН и оригиналов АВР(ЭАВР), ЭСФ»). При генерации заявки формулировка выбирается из списка и при необходимости правится под конкретный документ.
- **Контакт менеджера в документах.** В профиле пользователя — поля «Имя для документов» и «Телефон для документов»; подставляются в шапку заявок как контакт ответственного менеджера.
- Номера документов подставляются из системы (номер сделки/перевозки/счёта), дата — текущая с возможностью изменить.
- Хранилище файлов: все прикреплённые и сгенерированные файлы хранятся на сервере, привязаны к сущностям (сделка/перевозка/контрагент/счёт), максимальный размер файла настраивается (по умолчанию до 25 МБ).

### 4.6. Модуль «Коммуникации» (интеграции)

#### 4.6.1. WhatsApp через Wazzup
- Подключение существующего аккаунта Wazzup по API. **Официальная переписка ведётся с корпоративного номера**, подключённого к системе; переписка с личных номеров менеджеров системой не фиксируется — это организационное ограничение, которое нужно учитывать (см. организационные правила в разделе 7).
- Входящие и исходящие сообщения автоматически привязываются к контрагенту по номеру телефона и отображаются в его карточке и в ленте связанной сделки.
- Отправка сообщений из CRM: свободный текст + шаблоны (например, уведомление о смене статуса груза: «Ваш груз по заявке {{number}} прошёл таможню»).
- Если входящее сообщение от неизвестного номера — попадает в раздел «Неразобранные», откуда можно создать контрагента или привязать к существующему.

#### 4.6.2. Телефония (Asterisk/FreePBX + MicroSIP)
- Интеграция с существующей АТС Asterisk/FreePBX.
- При входящем звонке — всплывающая карточка: кто звонит (поиск по номеру в контрагентах), последние сделки.
- Журнал звонков в карточке контрагента: дата, направление (вход/исход), длительность, сотрудник, ссылка на запись разговора (если запись включена на АТС).
- Клик по номеру телефона в CRM — инициирует звонок через MicroSIP (протокол sip: / tel: ссылки либо через API АТС).
- Примечание для разработки: интеграция с телефонией — технически самый рискованный блок; выносится в отдельный этап (см. раздел 7) и не должна блокировать запуск остальной системы.

#### 4.6.3. Заявки с сайта (лиды)
- CRM предоставляет защищённый API-endpoint для приёма заявок с корпоративного сайта ava-solution.kz (форма: имя, телефон, email, маршрут «откуда → куда», описание груза, комментарий; набор полей настраивается).
- Защита: каждая заявка подписывается секретным ключом, известным только сайту и CRM; заявки без корректной подписи отбрасываются. На форме сайта — базовая антиспам-защита (honeypot-поле и/или простая проверка). Ограничение частоты запросов (rate limit) на стороне CRM.
- Поступившая заявка попадает в раздел «Новые заявки» (входящая очередь): система проверяет телефон/email по базе контрагентов — если контрагент найден, заявка привязывается к нему с пометкой «действующий клиент»; если нет — менеджер одним действием создаёт контрагента и сделку из заявки (данные переносятся автоматически).
- У каждой заявки сохраняется источник: страница сайта, языковая версия (рус/каз/кит), UTM-метки (если есть) — для аналитики каналов.
- Уведомление о новой заявке: внутрисистемное всем менеджерам (или дежурному — настраивается) + опционально в WhatsApp/Telegram.
- Правило распределения: заявка считается необработанной, пока по ней не создана сделка или не проставлен отказ с причиной; отчёт «скорость реакции на заявки» (время от поступления до первого действия менеджера).
- На стороне сайта: доработка формы (отправка на API вместо/помимо почты) входит в объём проекта; дубль на почту сохраняется как резервный канал на случай недоступности CRM.

#### 4.6.4. Email (второй приоритет)
- На первом этапе достаточно поля email в карточках и возможности отправки сгенерированных документов вручную. Полная синхронизация почты — за рамками текущего ТЗ, но архитектура не должна ей препятствовать.

### 4.7. Уведомления
- Внутри системы (колокольчик): назначили ответственным, просрочка по сделке, счёт просрочен, заявка на оплату ждёт согласования, груз просрочил плановую дату.
- Настройка: каждый пользователь может включить/выключить типы уведомлений для себя.
- Дублирование критичных уведомлений в WhatsApp сотруднику (опционально, через тот же Wazzup) или в Telegram-бота — на выбор при реализации, что проще и надёжнее.

### 4.8. Отчёты и дашборд
Главный экран руководителя:
- Активные перевозки по статусам (цифры + список).
- Воронка сделок за период: сколько заявок, сколько согласовано, конверсия.
- Финансы за период: выручка, расходы, маржа — всего и в разрезе юрлиц и менеджеров.
- Дебиторка/кредиторка: топ-должники.
- Кассовый календарь на ближайшие 2 недели.

Все отчёты: выбор периода, выгрузка в Excel (.xlsx).

### 4.9. Лиды и база обзвона (отдел холодных продаж)

Модуль для работы отдела Китая (и любого отдела активных продаж) с «сырыми» базами потенциальных клиентов. Ключевой принцип: **лиды хранятся отдельно от справочника контрагентов** — в контрагенты попадают только конвертированные (проявившие интерес), чтобы справочник не засорялся тысячами нерабочих записей.

- **Импорт базы:** загрузка Excel/CSV, маппинг колонок на поля (название, телефон, город, контакт, примечание — набор полей расширяемый), проверка дублей при импорте: по телефону/БИН против существующих контрагентов (пометка «уже наш клиент») и против других лидов (не задваивать). История импортов: какая база, когда, кем загружена, сколько записей.
- **Распределение:** руководитель отдела назначает лиды менеджерам (автоматически поровну или вручную пакетами); переназначение пакетом.
- **Статусы лида:** Новый → В работе → Перезвонить (с датой/временем) → Не дозвонились (счётчик попыток) → Не интересно (причина из справочника) → Конвертирован. Каждый звонок/касание фиксируется с датой и комментарием.
- **Экран «Мой обзвон»:** список лидов менеджера с запланированными на сегодня перезвонами наверху; фиксация итога звонка в один клик; после интеграции телефонии (Этап 4) — звонок кликом по номеру и автопривязка записи разговора.
- **Конвертация:** кнопка «Конвертировать» создаёт контрагента (данные лида переносятся, реквизиты дозаполняются парсером) + сделку в стадии «Расчёт ставки» с тем же ответственным; лид закрывается как «Конвертирован» со ссылкой на сделку.
- **Отчёты для руководителя отдела:** активность по менеджерам (звонки/дозвоны/конверсии за период), конверсия по базам импорта («из N лидов — M сделок»), причины отказов. Видимость по правилам отделов (раздел 3): менеджер видит свои лиды, руководитель отдела — лиды своего отдела.
- Лиды с сайта (раздел 4.6.3) и лиды обзвона — единый механизм с разным источником; источник сохраняется для аналитики.

## 5. Нефункциональные требования

1. **Тип системы:** веб-приложение, работает в браузере (Chrome, Edge). Установка программ на компьютеры сотрудников не требуется.
2. **Адаптивность:** интерфейс корректно отображается на экранах от 1280px; ключевые экраны (список перевозок, карточка сделки) должны быть пригодны к использованию и с телефона (адаптивная вёрстка), полноценная мобильная оптимизация — следующий этап.
3. **Одновременная работа:** до 15 пользователей одновременно без замедлений; страницы открываются не дольше 2 секунд при объёме до 50 000 сделок в базе.
4. **Безопасность:**
   - Вход по логину и паролю; пароли хранятся только в захешированном виде.
   - Обязательное HTTPS.
   - Сессия автоматически завершается после 12 часов неактивности.
   - Доступ к системе — только для авторизованных пользователей; никакие данные не доступны без входа.
   - Защита от базовых атак: SQL-инъекции, XSS, CSRF (использовать проверенные библиотеки, не писать самодельную криптографию и авторизацию).
5. **Резервное копирование:** автоматический бэкап базы данных и файлов минимум раз в сутки, хранение бэкапов за последние 30 дней, инструкция по восстановлению — обязательная часть поставки.
6. **Журналирование:** см. п. 3 — аудит изменений ключевых сущностей.
7. **Данные компании принадлежат компании:** система разворачивается на сервере, контролируемом компанией (VPS или облако по выбору), без привязки к сторонним SaaS, которые нельзя заменить.

## 6. Рекомендуемый технологический стек

(Выбран из соображений: популярность → AI-агенты хорошо пишут такой код; простота поддержки; один язык на клиенте и сервере.)

- **База данных:** PostgreSQL.
- **Бэкенд:** Node.js (TypeScript), фреймворк NestJS или Express + Prisma (ORM).
- **Фронтенд:** React (TypeScript), готовая библиотека компонентов (например, Ant Design — таблицы, формы, канбан из коробки).
- **Генерация документов:** docx-шаблоны через библиотеку docxtemplater (или аналог), конвертация в PDF через LibreOffice headless.
- **Развёртывание:** Docker Compose (приложение + база + бэкапы) на VPS. **Хостинг — VPS/VDS у PS.kz** (у компании там уже размещён сайт и есть аккаунт). Важно: обычный виртуальный хостинг PS.kz для CRM не подходит — требуется именно VPS с root-доступом. Стартовая конфигурация: 2 CPU / 2 ГБ RAM / 40 ГБ SSD (тариф уровня Basic-2), обязательно настроить swap-файл 2–4 ГБ для сглаживания пиков памяти при конвертации документов; генерация PDF — в фоновом режиме, по одной задаче за раз. При росте нагрузки — апгрейд тарифа без переустановки (4 ГБ RAM и выше); триггер апгрейда: простейший мониторинг памяти на сервере, при стабильной загрузке RAM выше ~85% — повышение тарифа. Ubuntu LTS. Данные системы физически хранятся в Казахстане.
- Окружения: тестовое и боевое (два VPS или два изолированных окружения на одном сервере); любые изменения сначала выкатываются на тестовое.
- Домен: поддомен основного сайта, например crm.ava-solution.kz, с SSL-сертификатом (Let's Encrypt, автообновление).
- **Репозиторий:** Git (GitHub, приватный), обязательные осмысленные коммиты по каждому блоку работ.

Допускается замена конкретных библиотек при сохранении принципов: TypeScript, PostgreSQL, контейнеризация, разделение тестового и боевого окружений.

## 7. Этапы разработки

Разработка ведётся поэтапно; каждый этап заканчивается работающей версией, которую можно посмотреть и потрогать.

**Этап 1 — Фундамент + Перевозки (трекер).**
Авторизация, роли, справочник контрагентов, сделки (упрощённо), перевозки с участками и 6 статусами, главный экран логиста. Результат: команда может вести все грузы в системе.

**Этап 2 — Финансы.**
Счета клиентам, заявки на оплату, мультивалютность и курсы, маржа по сделкам, дебиторка/кредиторка, кассовый календарь.

**Этап 3 — Документы.**
Шаблоны docx, генерация договоров/счетов/актов/доверенностей, реквизиты трёх юрлиц, файловое хранилище.

**Этап 4 — Коммуникации.**
Wazzup (WhatsApp), затем телефония Asterisk/MicroSIP, уведомления. Сюда же — модуль «Лиды и база обзвона» (раздел 4.9) для отдела Китая: импорт баз, обзвон, конвертация в сделки; базовая версия модуля (без телефонии, с ручной фиксацией звонков) может быть сделана раньше, если отделу нужно раньше съехать с Bitrix24.

**Этап 5 — Отчёты, дашборд, полировка.**
Дашборд руководителя, выгрузки в Excel, мобильная адаптация ключевых экранов, перенос данных. Миграция из двух источников: (а) контакты и сделки отдела по Китаю — экспорт из Bitrix24 в Excel → импорт; (б) реестр перевозок остальной команды — импорт из Google Таблиц (выгрузка в Excel, маппинг колонок на поля системы, предварительная чистка дублей силами владельца проекта).

Параллельный период: короткий — около 2 недель по активным перевозкам, либо тестовое наполнение системы реальными данными силами владельца проекта до подключения команды. Bitrix24 и Google Таблицы отключаются после того, как команда отработала параллельный период на этапах 1–3 без потерь данных.

**Организационные правила внедрения** (не код, но условие успеха; вводятся приказом по компании с Этапа 1):
1. Транспортная заявка перевозчику и счёт клиенту генерируются только из системы — вручную в Word такие документы больше не делаются.
2. Правило «нет в системе — нет оплаты»: финансист не проводит оплату субподрядчику без заявки на оплату, созданной в системе из участка перевозки.
3. Перевозка, не внесённая в систему или без даты выгрузки, не попадает в расчёт мотивации за месяц.
4. Официальная переписка с клиентами — с корпоративного WhatsApp-номера, подключённого к системе.

**Сопровождение после запуска:** после каждого этапа рекомендуется независимое ревью кода живым разработчиком (договорённость с доверенным внешним разработчиком); аварийное восстановление — по инструкции из поставки (см. п. 5.5) с помощью AI-инструментов и/или внешнего разработчика.

## 8. Критерии приёмки (как заказчик проверяет результат)

По каждому этапу заказчик проверяет по чек-листу, например для этапа 1:
1. Можно создать пользователя с ролью «Менеджер», и он не видит финансовые отчёты.
2. Можно создать контрагента, система предупреждает о дубле по БИН.
3. Можно создать сделку от каждого из трёх юрлиц — номера идут с правильными префиксами.
4. Можно создать перевозку с 3 участками и разными субподрядчиками, провести её по всем 6 статусам, история статусов сохраняется.
5. Просроченная перевозка подсвечивается в списке.
6. В журнале видно, кто и когда менял статус.

(Аналогичные чек-листы составляются перед началом каждого этапа и являются условием его закрытия.)

Дополнительные общие критерии:
- Ошибки уровня «данные потерялись/задвоились» — блокирующие, этап не принимается.
- К каждому этапу — краткая инструкция для сотрудников (1–2 страницы со скриншотами).
- Автоматические тесты минимум на критичную логику: расчёт маржи, статусы, права доступа.
